# BoopsDB WebUI・ネットワーク設定・クライアント更新の設計

作成日: 2026-10-04（日本時間）

調査基準: `df408bbad18ac19b48ca9c815df7c8a81f90e1b4`

状態: ユーザーによる内容承認済み。実装計画を作成する段階。

## 目的と対象

`boops-webui` の情報を探しやすくし、編集後も表示順を保つ。複数 NIC の設定では、デフォルトゲートウェイを持つ NIC を選択できるようにする。`boops-client` は空のゲートウェイを OS 設定へ反映し、配布先の最新版を自動適用する。

対象は `boops-webui`、必要な `boops-server` の API、`boops-client`、クライアントのビルド・配布処理と説明書である。旧 `boops-ui` と `boops-cli` は今回の変更対象に含めない。稼働中の DB、端末、WebUI の本番環境にはこの開発作業から設定変更を実行しない。修正版クライアントの配布先へのアップロードはユーザーの依頼範囲に含む。

## 調査で確認した問題

| 対象 | 現状 | 変更が必要な理由 |
| --- | --- | --- |
| WebUI のテーマ | Vuetify の初期テーマとスイッチの初期値が一致せず、選択も保存されない | 初期表示と切替後の見た目を揃える |
| 一覧と NIC・IP の順序 | 一部の SQL に `ORDER BY` がなく、編集後に全体を再取得する | 保存前後で行の位置が変わり得る |
| 行の識別 | IP 行のキーに配列の位置を使う。マシン検索表は hostname を行 ID に使う | 追加・削除や同名マシンを安定して扱えない |
| ゲートウェイ | API は空を保存できるが、複数 NIC の非空値を制限しない | 利用する NIC を選べない |
| 空値の反映 | nmcli・Windows の経路では空値時の解除が明示されない | API を空にしても既存ゲートウェイが残り得る |
| Netplan | NIC ごとに全 YAML を削除し、同じファイルへ 1 NIC 分だけ出力する | 複数 NIC を保持できず、対象外の設定も失い得る |
| 同期状態 | ネットワーク適用が失敗しても状態を保存する | 次の同期で失敗した変更が再試行されない |
| 更新と配布 | 固定名の 0.1／0.2 バイナリのみ。最新版情報と更新処理がない | 配布ファイルを更新しても既存端末には届かない |

調査時点の作業ツリーはクリーンだった。`go test ./...` は成功したが、現行クライアントにテストファイルはない。WebUI は依存関係を未導入で、ビルドと実画面の確認は未実施である。

## WebUI の構成と表示順

### 見た目とテーマ

既存の Nuxt・Vuetify を使う。Google Cloud Console を参考に、上部ヘッダー、左ナビゲーション、ページ見出し、操作バー、情報量を揃えた表とカードで構成する。アクセントは青、背景と区切り線はテーマの色を使う。PC では左ナビを表示し、狭い画面では開閉式にする。検索、一覧、登録、詳細の既存機能をこの構成に収める。

テーマは「システム」「ライト」「ダーク」の 3 通りとし、選択を Cookie に保存する。初回は OS の配色設定に従う。Cookie と OS 設定をクライアント初期化時に解決し、Vuetify へ適用してからテーマに依存する画面を表示する。SSR では `ClientOnly` の背景付きプレースホルダーを使い、未選択・システム選択時の色は CSS の `prefers-color-scheme` に従わせる。これにより SSR の DOM と初期化後の DOM の不一致を避ける。システム選択中は OS 設定の変更を監視する。固定の白文字・背景色を整理し、フォーカス、入力欄、エラー、無効状態も両テーマで確認する。

左ナビのリンクは一覧・検索の `/` と `/machines`、新規登録の `/machines/register` とし、詳細 `/machines/:id` では一覧の階層を選択状態にする。狭い画面ではヘッダーのボタンから開き、ページ選択・Escape・背景クリックで閉じる。ボタンに用途を示すラベルを付け、キーボード操作と閉じた後のフォーカスの復帰を確認する。旧メニューの未使用ルートは残さない。

マシン詳細は「基本情報」「ネットワークインターフェース」を分ける。基本情報の項目順は固定する。各 NIC は独立した枠付きカードとし、ヘッダーに NIC 名と操作を置く。内部を「識別情報」「IP アドレス」「ゲートウェイ・DNS」に分け、どの NIC を編集しているかを明示する。追加フォームは既存 NIC の後ろに独立して置く。

### 順序と行の識別

既定のマシン一覧は登録日時の昇順、同値時はマシン ID の昇順とする。登録日時が NULL の既存行は最後に ID 昇順で並べる。SQL の既定条件は `created_at IS NULL ASC, created_at ASC, id ASC` である。NIC・IP は登録時の順序を基本とし、既存データには `id ASC` を適用する。通常の項目編集、NIC 名の変更、ゲートウェイの選択、DNS の保存で順序を変えない。ドラッグによる任意の並べ替えは今回追加しない。

検索で並べ替え条件を指定していない場合も登録日時順を使う。明示的な並べ替え条件は維持し、同値時の ID を SQL の第 2 条件にする。ページ間と再検索で同じ順序を使い、WebUI 側だけで取得済みページを別条件に並べ替えない。検索条件・並べ替えを画面遷移後も復元できるようにする。ユーザーが明示的に選んだソート対象を編集した場合は、その条件に沿った移動を許容する。

マシン行は UUID、NIC は DB の ID、保存済み IP は IP 行の ID で識別する。GET の IP 情報へ ID を追加する変更は既存クライアントに対して追加フィールドとして扱える。未保存 IP には画面内だけの固定 ID を与え、入力中に配列の位置をキーにしない。

全マシン PUT でも、同名 NIC を全削除・再作成せず既存 ID を保つ。IP 編集は既存行を IP 行 ID で更新し、削除・新規追加を区別する。ID を送らない旧 API 利用者は、同じアドレス・サブネットの既存行を ID 昇順に 1 行ずつ対応付ける。同じ値が複数ある場合も、要求内の出現順と対応付けて行を重複利用しない。対応する既存行がない値は新規行として送信順で末尾へ追加する。ID が別 NIC の行を指す要求や同一 ID の重複は拒否する。既存行の順序は保持し、新規 NIC と IP は末尾へ追加する。クライアントの設定比較は NIC 名と IP の内容を使い、表示順だけの変化では OS 設定を再適用しない。

全マシン PUT の `interfaces` は従来通り NIC 名をキーにした object とする。value に任意の `id`、`ips` の各要素に任意の `id` を追加する。NIC ID を指定すると名前の変更でも既存 NIC と対応付けられる。NIC 専用の名前変更 API も既存 ID を維持する。IP 専用更新 API は従来の `{ "ips": [...] }` の各要素へ ID を追加できる。未知の ID、他マシン／他 NIC の ID、重複 ID、最終的な NIC 名の重複は 400 とする。同名 NIC が複数存在する既存 DB に名前だけで更新する要求は 409 とし、勝手に 1 行を選ばない。全マシン PUT の明示 ID 付き要求では、一意な新しい名前へ整理できる。

全マシン PUT の NIC 集合は完全置換とする。`interfaces` は必須、空 object は全 NIC の明示的な削除である。要求に含まれない NIC は削除し、含まれない IP 行も削除する。含まれる NIC の `ips` は 1 個以上を必要とし、WebUI は最後の IP 行を削除できないようにする。要求全体の構造・値を先に検証し、トランザクション内で所有関係と既存集合を確認してから更新・削除・追加する。子の IP を削除してから NIC を削除し、途中失敗は machine の値を含めてすべて rollback する。専用 IP 更新でも検証失敗後に削除済み状態を残さず、全経路で接続を解放する。

## ゲートウェイの契約とクライアントへの反映

### API と WebUI

既存の `interfaces.gateway` を使い、同じマシンで非空ゲートウェイを持つ NIC を 0 または 1 つとする。新しい選択用 DB 列は作らない。WebUI は NIC ごとに「デフォルトゲートウェイに使用」を示し、選択した NIC でアドレスを入力する。利用しない NIC の gateway は空文字である。「ゲートウェイなし」は選択 NIC がない状態とし、空のアドレスのまま選択を保存しない。

空文字、`null`、空白のみ、従来の「未設定」値 `0.0.0.0` は空文字に正規化する。今回のネットワーク適用は現行と同じ IPv4 を対象とし、非空ゲートウェイには IPv4 アドレスを要求する。GET は未設定 gateway を常に `""` で返す。同じ正規化関数を GET、全書込み、既存値の競合判定に使い、NULL・空白・`0.0.0.0` をゲートウェイの個数に数えない。クライアント側も同じ意味で正規化する。

ゲートウェイ専用 PUT で非空値を指定した場合は、同じトランザクション内で他の NIC の gateway を空にして対象を更新する。マシン行を共通のロック対象にし、同時に別 NIC を選択しても非空値が複数残らないようにする。空への更新は対象 NIC のみを解除する。同じ値を再送しても、対象が存在すれば成功を返す。

POST machine・PUT machine の複数 NIC の要求は、非空値が 2 つ以上なら SQL の書込み前に 400 とし、何も保存しない。POST interface で非空値を指定した場合は、その NIC を選択する操作として他を同時に解除する。既存マシンに対する全 NIC 書込みとマシン削除は、トランザクション開始、machine 行の `FOR UPDATE`、必要な子行の取得・更新の順に統一する。これには POST interface、全 machine PUT、gateway PUT、名前・IP・DNS・MAC の専用更新、NIC／machine の削除、および登録用 API の NIC 書込みも含む。新規 POST machine は入力を検証してから 1 トランザクションで machine と子を作成する。WebUI は保存後にマシン全体を再取得し、解除された他 NIC の表示も更新する。

既存 DB に複数の非空 gateway がある場合は、読み取りで勝手に選択しない。WebUI に状態を示して利用する NIC の選択を促す。クライアントはこの設定を OS へ適用せず、どの NIC が競合したかを報告する。ユーザーが選択すると既存値をまとめて整理できる。開発作業中に本番 DB の値を変更しない。

### クライアントの検証とネットワーク適用

API の全 NIC を検証してから OS 設定を変更する。NIC 名の欠落・重複、形式不正、複数の非空 gateway は適用前に失敗させる。登録情報の収集では NIC 名を確実に設定する。設定比較は NIC 名をキーとし、IP の順序には依存せず、gateway・DNS・MAC・IP の設定内容の変化を検出する。

Linux の対象 NIC の存在を先に確認し、全 NIC 分の設定を生成してから反映する。方式別の処理は次のとおりとする。

| 方式 | 反映方法 |
| --- | --- |
| Netplan | 現行の対象ファイル `01-netcfg.yaml` をバックアップし、全対象 NIC を 1 回で更新する。YAML を構造として読み書きし、対象外 NIC・bridge・VLAN 等を保持する。対象 NIC の IPv4 default route と旧 `gateway4` は解除・置換し、default route は選択 NIC にだけ出力する。他ファイルを削除しない。生成検証後に apply を 1 回実行する |
| `/etc/network/interfaces` | 元ファイルをバックアップし、全対象 NIC の設定を 1 回の書込みで更新する。空 gateway には gateway 行を出力せず、対象外の定義を保持する。対象 NIC の `up`／`post-up` 等に default route を追加する独自コマンドがあれば、意味を推測して削除せず、書込み前に競合として停止する |
| NetworkManager | 接続を NIC に対応付ける。選択 NIC の gateway を設定し、未選択 NIC は gateway をクリアして `ipv4.never-default` を有効にする。対象 NIC の IPv4 default route を持つ静的経路も整理し、通常の静的経路は保持する。全設定を検証してから接続を反映する |
| Windows | 空 gateway を明示的に解除する設定を生成し、コマンド失敗を呼出し元へ返す。ネットワーク処理の現行対応を維持するが、今回の自動更新配布は Linux のみとする |

Netplan は有効な設定を `/lib/netplan`、`/etc/netplan`、`/run/netplan` の優先順位を含めて確認する。対象ファイル以外にも対象 NIC のアドレス・DHCP・default route が定義されている場合は、書込み前に競合として停止する。読み取り対象を増やしても変更対象は `/etc/netplan/01-netcfg.yaml` のみとする。ifupdown の `source`／`source-directory` で取り込まれた対象 NIC の別定義も競合として扱う。外部設定を黙って削除しない。Netplan の構造の保持には YAML ライブラリを利用できるが、他の機能のための依存追加は行わない。

設定ファイルは検証後に同じディレクトリの一時ファイルから置換する。生成・適用に失敗した場合は元ファイルを復元し、OS への復元が失敗した場合も含めてエラーを返す。複数 NIC の実際の切替を OS 全体で原子的に保証するとは表現しない。

ネットワーク適用が成功した場合だけ `machine_state.json` を保存する。失敗した gateway の解除や変更は次回も再試行する。UUID を持つ `config.json` はネットワーク変更や更新で書き換えない。

## 自動更新・初回移行・配布

### 更新の実行

自動更新の対象は配布中の Linux amd64・arm64 である。更新処理は Go クライアント内に置き、`sync` の設定読込み後、API 同期に入る前に実行する。API 障害や JSON 不正で同期が失敗しても更新確認が可能な位置にする。更新確認が失敗した場合は現行バイナリで通常の同期を続ける。

更新確認は既定で 1 時間に 1 回とし、1 分ごとの同期では前回確認時刻をローカルに保存して取得を抑える。通信失敗後も次の定期確認まで待ち、強制確認は明示的な `boops update` で行えるようにする。`boops version` を追加する。開発用ビルド・非対応 OS は自動置換しない。`config.json` に任意の boolean `auto_update` を追加し、false の場合に無効、欠落時は有効とする。再登録時も ID 以外の既存キーを保持して更新する。

署名された最新版情報を読み、現在のバージョンより新しい場合だけ取得する。正規の 3 要素バージョンで比較し、古い版へは自動で戻さない。新バイナリを同じディレクトリの一時ファイルへ保存し、サイズと SHA-256、実行権限、`version` コマンドの結果を確認する。成功後に旧版の復旧用コピーを保持して実行ファイルを原子的に置換する。置換した同期は終了し、次のタイマー起動から新版を使用する。

通信失敗、署名不一致、ハッシュ不一致、起動検査失敗、保存・置換失敗では現行バイナリを保持する。更新確認状態は `/etc/boops/update-state.json` に分離し、`config.json` と `machine_state.json` の内容を保持する。状態は `last_check` に UTC の確認開始時刻を保存する。欠落・破損・未来の時刻は次回確認が必要な状態とする。状態はバイナリとは別に一時ファイルから原子的に置換する。

更新と同期の同時実行で二重に置換されないよう、Linux の `/etc/boops/update.lock` に非ブロックのプロセス間ロックを使う。ロック取得後に確認状態を読み、時刻を判定する。定期同期がロックを取得できない場合は更新だけをスキップして通常同期を続ける。`boops update` が取得できない場合は「別の更新処理が実行中」と報告して終了する。ロックファイルが残っていても、プロセスのロックが解放されれば次の実行を妨げない。

置換後のすべての動作を試験できるわけではない。旧版の復旧用コピーは手動復旧に使うものとし、起動後の自動ロールバックは今回実装しない。

### 配布情報と署名

配布先は `https://file.booyah.dev/BoopsDB-Client/` とする。最初の修正版は `0.3.0`、バイナリ名は `boops_0.3.0_amd64.binary` と `boops_0.3.0_arm64.binary` とする。既存の 0.1／0.2 ファイルを上書きしない。

`latest.json` は署名対象 JSON の UTF-8 生バイトを標準 Base64 にした `payload` と、64 バイトの Ed25519 署名を標準 Base64 にした `signature` を持つ単一ファイルとする。署名対象は Base64 を decode した payload の生バイトであり、JSON の再シリアライズや Base64 文字列そのものには署名しない。署名対象には形式バージョン `1`、クライアントバージョン、OS／arch ごとの相対ファイル名、サイズ、SHA-256 を含める。クライアントは埋込み公開鍵で署名を検証してから、その中身を信頼する。鍵を manifest から受け取らない。Go には 32 バイトの公開鍵を固定し、インストーラーには同じ鍵の SubjectPublicKeyInfo PEM を固定する。

取得は HTTPS の固定配布先だけを許可する。パストラバーサル、別ホストへの URL、別ホストや HTTP へのリダイレクトを拒否する。manifest は 1 MiB、バイナリは 64 MiB を上限とし、manifest 取得は 15 秒、バイナリ取得は 120 秒で打ち切る。HTTP 成功応答を必要とし、エラーページをバイナリとして保存しない。

署名秘密鍵はリポジトリと配布先に保存しない。初回リリース時にユーザー環境の別ディレクトリへ権限を限定して保存し、公開鍵だけをソースと配布説明に含める。鍵の保管場所と今後のリリース方法を説明する。CI は署名鍵が利用可能なリリース実行だけを公開可能とし、PR のテストではアップロードしない。単なる main への push でも公開済みバージョンを上書きしない。今回の鍵ローテーション機構は設けない。交換が必要になった場合は、旧鍵で署名して新しい公開鍵を組み込んだ版を配布するか、旧鍵が使えない場合は初回移行と同じ手動導入で切り替える。

配布処理は 2 アーキテクチャをビルド・検証し、バイナリをアップロードして同じ URL から再取得する。サイズと SHA-256 の一致を確認した後に `latest.json` を公開する。最後に公開された `latest.json` を読み戻し、署名・バージョン・両バイナリの一致を確認する。成果物と検証結果はローカルにも残す。

### 既存端末の初回移行

旧版には更新処理がないため、配布先へのアップロードだけでは移行できない。新しいインストーラーを提供し、一度実行すると、その後は定期同期で更新できるようにする。新規登録と既存端末の更新を分け、既存 ID と同期状態を維持する。更新時は元の有効・稼働状態を記録し、timer 停止、実行中 service 停止、ダウンロードと検証、原子的なバイナリ置換、元の timer 状態の復元の順で処理する。既存 ID がある場合は `regist` を呼ばず、`config.json` と `machine_state.json` のバイト列を変更しない。非アクティブなタイマーを勝手に起動しない。

実装計画のための追加確認で、現行の `regist` は存在しない `POST /api/machines/:id` に送信し、404 でも成功を表示することが分かった。新しい `regist <machine-id>` は、WebUI で作成済みのマシンを `GET /api/machines/:id` で確認してからローカルに ID を保存する。取得失敗・ID 不一致の場合は保存しない。登録のためにサーバーの NIC 設定を置き換えず、初回同期で API の設定を適用する。既存の登録コマンド名と ID の指定方法は維持する。

インストーラーは最新情報の署名とダウンロードしたバイナリを検証し、一時ファイルから置換する。検証用公開鍵はインストーラーに固定する。JSON と Base64 の処理に Python 3、署名検証に OpenSSL 3.0 以上を必要とし、非対応の場合は未検証のインストールを続行しない。必要なコマンドは導入説明に記載する。検証は `openssl pkeyutl -verify -rawin -pubin -inkey public-key.pem -in payload.json -sigfile signature.bin` とし、Go と同じ payload の生バイトを使う。仕様の根拠は [OpenSSL の公式文書](https://docs.openssl.org/3.0/man1/openssl-pkeyutl/) である。

新規導入時はバイナリを用意して設定・登録が済んでからタイマーを有効化する。失敗時には旧バイナリと既存設定を保持し、停止したタイマーの状態を復元する。サービス・タイマーは今回の配布物としてインストーラーに含め、独立した未検証のネットワーク応答で置き換えない。更新済みの `install_0.3.sh` と今後の入口となる `install.sh` を配布する。旧インストーラーは履歴として残す。

本番 DB・実 NIC の変更を伴わない試験を先に行う。テスト用 HTTP、DB、コマンド実行と一時ファイルで失敗条件を再現し、現行の問題を検出するテストを修正前に確認する。
